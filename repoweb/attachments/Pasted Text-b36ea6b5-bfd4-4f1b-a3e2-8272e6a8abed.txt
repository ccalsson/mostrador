Actualmente existe este problema:

Carrito:
    Tenant A → válido
    Tenant B → inexistente/inválido

Resultado actual:

    PERO Tenant A queda creado
    Y su stock queda reservado

Esto es incorrecto.

El checkout debe ser atómico.

El resultado debe ser:

TODOS LOS PEDIDOS VÁLIDOS
        +
TODAS LAS RESERVAS VÁLIDAS

       COMMIT

CUALQUIER ERROR
        ↓
     ROLLBACK
        ↓
NO queda ningún pedido
NO queda ninguna reserva
NO queda descuento de stock

La operación debe utilizar una única transacción de base de datos cuando técnicamente corresponda.

No implementes una segunda lógica de stock.

Debe continuar utilizando:

reservarLineas
soltarReserva

y la lógica existente de Mostrador.

Pero el conjunto de operaciones del checkout multi-tenant debe quedar correctamente protegido contra resultados parciales.

Prueba obligatoria

Reproducir:

Pedido A → tenant válido
Pedido B → tenant inexistente

Resultado esperado:

HTTP error
+
Pedido A NO existe
+
Pedido B NO existe

stock A permanece igual
+
ninguna reserva queda pendiente

Pedido A → válido
Pedido B → válido

y entonces:

Resolverlo de una de estas dos formas, eligiendo la que mejor respete el modelo existente:

PREPARADO

Preferir A si no rompe el flujo real de Mostrador.
